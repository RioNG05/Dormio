# MODULE 1 — BHMS: Tenant Use Cases

**Module**: Boarding House Management System (BHMS)
**Actor**: Tenant (Người thuê trọ)
**Global rules**: See `docs/spec/00-global-conventions.md`

---

## UC-T-01 — Receive Onboarding Notification
**Tier:** Free

Triggered inside the same transaction as UC-L-04 step 8 / UC-L-04b step 6.

Insert `NOTIFICATION(sender_id=<landlord>, receiver_id=<tenant>, type='contract_created')`, then **enqueue an async job** to dispatch SMS/Zalo/Email. Do not call 3rd-party APIs synchronously inside the contract-creation transaction — a flaky SMS provider must never block contract creation.

---

## UC-T-02 — Receive Billing Notification
**Tier:** Free

Triggered by the same cron job as UC-L-06 step 1, immediately after `INVOICE` creation.

Insert `NOTIFICATION(receiver_id=<tenant>, type='billing_due', content=<amount + deep link to /invoices/:id>)`, dispatch via async job.

---

## UC-T-03 — Upload Utility Meters via OCR
**Tier:** Free · **Tech:** OCR API

**Flow:**
1. Tenant uploads image → store immediately, create `METER_READING(room_id, service_id, period, image_url, status='pending')`.
2. Async OCR job extracts `reading_value` → `UPDATE METER_READING SET reading_value=..., status='pending'` (OCR result is a suggestion, not final).
3. Tenant reviews extracted number:
   - **Confirm** → `status='confirmed'`
   - **Retake** → tenant re-uploads; update the same `METER_READING` row in-place (same `id`, not a new row, since not yet confirmed).
4. Only `status='confirmed'` readings feed into UC-L-06 invoice generation.

---

## UC-T-04 — Execute Direct Payment
**Tier:** Free

Reads the `INVOICE` generated by UC-L-06, renders the same locked-amount VietQR. On webhook confirmation, same `PAYMENT` insert logic as UC-L-06 step 5 — **this is the same backend flow, not a separate implementation**.

---

## UC-T-05 — View Usage Analytics
**Tier:** Free

Query `METER_READING` + `INVOICE_DETAIL` for the tenant's current active `CONTRACT.room_id`, grouped by `period`.

Tenant-scoped — verify `CONTRACT_TENANT.tenant_id = current_user.id` before returning any data.

---

## UC-T-06 — View Tenancy Details
**Tier:** Free

Read-only aggregate:
- `CONTRACT` (active, for this tenant)
- `ROOM`
- `BOARDING_HOUSE` (basic info only, not financials)
- `NOTIFICATION WHERE boarding_house_id=... AND receiver_id IS NULL` (broadcast announcements)
- `ROOM_SERVICE` (fee structure)

## UC-T-07 — Submit Grievance / Complaint
**Tier:** Free

**New table required** (not in original ERD — add via migration):

```
GRIEVANCE
  id              PK UUID
  tenant_id       FK → USER  (onDelete: Restrict)
  boarding_house_id  FK → BOARDING_HOUSE nullable (context only)
  category        enum: overcharging | harassment | maintenance | other
  content         text
  status          enum: open | in_review | resolved | rejected  (default: open)
  resolution_note text nullable
  resolved_by     FK → USER nullable (admin who resolved it)
  created_at      timestamp
  resolved_at     timestamp nullable
```

**Flow:**
1. Tenant creates `GRIEVANCE(status='open')`.
2. Routes to Admin queue (UC-A-04).
3. Admin updates `status` / `resolution_note`.
4. On resolution: trigger notification to tenant via Email/Zalo (async job).
5. Tenant polls/subscribes to their own `GRIEVANCE` rows for status tracking.
